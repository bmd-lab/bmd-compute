# Structure Search (USPEX) — Design

Status: **design, not implemented.** Tracking issue: #58.

This document is the single reference for adding USPEX crystal structure
prediction to bmd-compute. It records the design, the lab decisions taken so
far, what was checked on POWER (with the commands that reproduce each check),
what the USPEX 25.0 manual confirms, and what is still open. Implementation
pull requests should refer to this document and update it when they change
something it says.

Conventions in this document:

- **Checked** means run or read and the result recorded here.
- **Inferred** means reasoned from evidence but not directly confirmed.
- **Open** means not yet known.
- Manual section numbers (§) refer to the USPEX 25.0 manual dated
  9 November 2025, installed on POWER at
  `/powerapps/share/rocky9/uspex-25/uspex_manual_english_v2025.pdf`.

## 1. Goal and scope

Let BMD Lab members run USPEX evolutionary structure searches through
bmd-compute, with VASP relaxations on `leeburton-pool`, and send the best
candidates into the existing Relaxed Energy, Phonons and Band Structure
workflows. The final ranking of candidates comes from BMD-provenanced
energies, not from USPEX's search-grade energies.

In scope first:

- fixed composition (`calculationType = 300`), PBE, non-magnetic
- VASP for every relaxation step

Later, not in Phases 0–2:

- variable composition (`calculationType = 301`) and convex-hull plots
- spin and DFT+U for searches
- MatterSim pre-relaxation steps (bundled with USPEX 25, see §6)
- seeding searches from the lab's database of experimental frameworks

## 3. How USPEX fits bmd-compute

| Area | bmd-compute v1 today | USPEX 25.0 | Consequence |
|---|---|---|---|
| Input | one `pymatgen.Structure` | composition (`atomType`, `numSpecies`), pressure, atoms-per-cell range | new entry point and spec (#64) |
| Size | stage list fixed at build time | adaptive: `initialPopSize` + `populationSize` × generations, early stop via `stopCrit` | required explicit walltime; no automatic estimate |
| Control process | `run_job.py` inside the sbatch allocation | one long-running master (`./uspex`, §2.7) that polls every `sleepSeconds` | master runs inside the allocation |
| VASP inputs | generated by BMD policy; free-form INCAR rejected | `Specific/INCAR_1..N` copied verbatim to every candidate; KPOINTS from `KresolStart` (one value per step, units 2π Å⁻¹, §4.8) | BMD generates the INCAR ladder (#65) |
| Error handling | Custodian; an unconverged stage fails the workflow | no Custodian; poor relaxations are scored and discarded by the search | no Custodian in searches |
| Restart | a rerun is a new attempt in a new directory | rerun in the same folder continues; each restart writes `results2/`, `results3/`, … (§3.2, §4.7) | resume exception (#69); parsers read every `results*/` |
| Outputs | final-stage VASP files parsed remotely | `results*/Individuals`, `BESTIndividuals`, `gatheredPOSCARS`, `goodStructures_POSCARS`, `OUTPUT.txt` | new parser (#62) |
| Cancel | no cancel route | — | cancel for searches (#69) |

What can be reused unchanged: `RemoteRunner`, the verified runtime package
upload, the submission ledger and idempotent submission, SLURM-state
monitoring, the remote result-parser pattern, and the Plotly line-plot
renderer.

## 4. Architecture (option A with a launch bridge)

One exclusive-node SLURM job per search attempt:

```
sbatch (-N 1 --exclusive --mem=0, owner100d, explicit walltime)
  run_job.py (host)
    ├─ singularity exec -B /bmd <sandbox> /opt/uspex/uspex      USPEX master
    │    whichCluster = 0, numParallelCalcs = 4, coresPerJob = 1
    │    commandExecutable (one line per step) = sh bmd_bridge.sh <step>
    │       bridge script: write request file → wait for done file
    └─ launch loop (host): request → srun --exact --mpi=pmi2 -n 48 --mem=<M> vasp_std
                                     in that CalcFold → write done file
```

Why the bridge: USPEX 25 runs only inside its Singularity image (it needs
glibc 2.35; §5), and the image has no `srun`, no SLURM configuration and no
`python3`. The bridge needs only `sh`, `flock`, `timeout` and `sleep`, which
the image has.

Why this works with USPEX (checked in the manual):

- `whichCluster`: −1 = local run without job submission; 0 = local run with
  strict CPU core control (each relaxation on its own cores, `coresPerJob`);
  0 is the default (§2.8, §4.8). `numParallelCalcs` "now works for
  whichCluster = 0 as well" (§2.8).
- `commandExecutable` takes one shell command per relaxation step, run in the
  calculation folder; USPEX waits for it and then reads the VASP output (§4.8).
- `whichCluster = 1` (local submission) is not usable in the container: it
  needs an ssh server on the local machine and Python job scripts (§6.8.1).
- `coresPerJob = 1` makes USPEX's own core control pin only the waiting bridge
  script; SLURM places the VASP ranks.
- `numParallelCalcs` must always be set explicitly: §4.8 gives its default as
  1, §2.8 says it auto-detects available cores, which on a 192-core node could
  mean 192 concurrent relaxations.

Why 4 × 48 ranks (inferred, to be measured): the lab's VASP benchmarks
measured four concurrent 48-rank PBE jobs at 2.09× the throughput of one
192-rank job, but on a 3-atom Sc₂C cell with 65 irreducible k-points. USPEX
candidates are larger cells with varying k-point counts, so Phase 0 measures
4 × 48 against 8 × 24 on a real search.

Intel MPI: set `I_MPI_DEBUG=4` and never set `I_MPI_PIN_DOMAIN` (in the lab's
benchmarks it silently overrode the processor list and placed concurrent jobs
on the same cores).

Rejected alternatives:

- **One sbatch per relaxation** from a driver job: scales beyond one node, but
  child jobs are invisible to bmd-compute's one-job-per-attempt monitoring and
  can be orphaned. Possible later for searches larger than one node.
- **USPEX master on the bmd-compute web VM** (`whichCluster = 2`): puts a
  long-lived scientific process on the web host, which has a single Uvicorn
  process with no durable state.
- **Binding host `srun`, SLURM libraries, `/etc/slurm` and munge into the
  container**: depends on host library versions; more fragile than the bridge.

## 5. USPEX on POWER: checked facts

All checks run on 2026-11-01 from a login node and compute nodes of
`leeburton-pool`. Commands are given so anyone can repeat them.

### 5.1 Installs

| Install | Location | Notes |
|---|---|---|
| `uspex-25` module | `/powerapps/share/rocky9/uspex-25/` | `uspex_25.sif` (Singularity image), `uspex` (self-extracting file), `uspex25.def` (image recipe), the 25.0 manual |
| `USPEX-10.5` module | `/powerapps/share/rocky9/uspex-10.5` | MATLAB runtime (`MCRROOT`); not used |

```bash
module avail 2>&1 | grep -i uspex
module show uspex-25
cat /powerapps/share/rocky9/uspex-25/uspex25.def
```

The image recipe is Ubuntu 22.04 plus `libgomp1` and coreutils, with the same
`uspex` file copied to `/opt/uspex/uspex`. Its `%environment` resets `PATH`.
Loading the `uspex-25` module also activates a conda/Singularity environment;
bmd-compute should call Singularity and the image by full path instead.

### 5.2 The `uspex` self-extracting file

- POSIX shell script with a gzip tar payload; banner "USPEX v25.0, 11 November
  2025"; `PAYLOAD_SHA256=fc4a08e65ffc5f4fc3b45cb058de2cd54731ab2c191123aac8a3c69e87e95c8c`.
- Unpacks once, under an `flock` lock, to `$XDG_CACHE_HOME/uspex_sfx/<sha>/`
  (default `~/.cache/uspex_sfx`, fallback `/tmp/uspex_sfx_$USER`), marks it
  `.ready`, then runs `uspex_core/uspex`. Later starts skip unpacking.
- Unpacked size 2.0 GB; unpacking took about 54 s onto `/bmd` (NFSv4).
- Home quotas are too small: the unpack fails with "Disk quota exceeded".
  Use group storage under `/bmd` and set `XDG_CACHE_HOME` for the USPEX
  command only.
- If an unpack is interrupted after the final `mv` but before `.ready`, the
  next run moves a fresh copy *inside* the old folder and fails; delete
  `uspex_sfx/<sha>*` and unpack again. bmd-compute should unpack once at
  environment setup and only check `.ready` at job start.

```bash
head -c 20000 /powerapps/share/rocky9/uspex-25/uspex | strings -n 3 | head -80
```

### 5.3 Host vs container

Directly on a Rocky 9.7 compute node the unpacked program fails:

```
uspex_core/uspex: /lib64/libm.so.6: version `GLIBC_2.35' not found
```

Inside the image it starts (glibc 2.35). Run in an empty folder it does not
report a missing `INPUT.txt`; it starts the algorithm and crashes with an
`IndexError` in `calculate_formation_energies`. bmd-compute must always write
a complete, validated `INPUT.txt`.

Tools inside the image: `sh`, `bash`, `flock`, `timeout`, `sleep`, `tail`,
`awk` present; `python3` and `srun` missing.

```bash
srun -p leeburton-pool -N 1 -n 1 -t 00:10:00 bash -lc 'module load uspex-25 >/dev/null 2>&1; singularity exec -B /bmd "$USPEX_SIF" sh -c "for c in sh bash python3 flock timeout sleep tail awk srun; do printf \"%-8s \" \$c; command -v \$c || echo MISSING; done"'
```

### 5.4 Sandbox

Singularity 3.8.6 converts the SIF to a temporary sandbox on every start.
USPEX is one long-running process, so this costs once per allocation; a
prebuilt sandbox is a convenience. `singularity build --sandbox` fails
("unsquashfs not found", although `unsquashfs` is in the module's mamba
environment). A sandbox built by hand works:

```bash
srun -p leeburton-pool -N 1 -n 1 -t 00:30:00 bash -lc 'module load uspex-25 >/dev/null 2>&1; cd /bmd/shared && singularity sif dump 4 "$USPEX_SIF" > uspex25.sqfs && unsquashfs -d uspex25_sandbox uspex25.sqfs && rm uspex25.sqfs'
```

(Partition 4 is the squashfs partition listed by `singularity sif list`.) The
sandbox must be group-readable for `bmdguest`.

### 5.5 Other cluster facts relevant here

- Compute nodes run Rocky Linux 9.7. `backend/config.py` loads
  `intel/rocky8-oneAPI-2023` and `vasp/rocky8-intel-6.4.1`; whether these
  still load on the nodes is **open** (#59).
- `compute-0-332` and `compute-0-333` have a different NUMA layout and were
  not part of the lab's VASP benchmarks; pilots exclude them.
- Strings inside the USPEX 25 program show that `commandExecutable` and
  `coresPerJob` take one value per relaxation step (error text: "number of
  commandExecutable entries is not equal to the number of steps").

## 6. VASP policy for searches (to be reviewed, #65)

USPEX 25.0 manual recommendations (§3.1): 4–5 relaxation steps; ISIF 4 in
steps 1–2, ISIF 3 in steps 3–4 with ENCUT raised 30–40 %, a final
single-point step (ISIF 2, NSW 0); EDIFF 1e-2 → 1e-4 and EDIFFG 1e-1 → 1e-3;
IBRION 2 (POTIM 0.02) far from a minimum, IBRION 1 (POTIM 0.3) near one;
Methfessel–Paxton smearing (ISMEAR 1) for every system, SIGMA 0.10 → 0.05,
because many sampled structures are metallic. Pressure is set only by
`ExternalPressure` in `INPUT.txt`; do not put `PSTRESS` in the INCARs (§4.1).
The enthalpy is taken from the last step (§4.8, `abinitioCode`).

Proposal to review against BMD standards (`docs/methodology.md`):

- Steps that change volume (ISIF 3) use the BMD relaxation ENCUT (580 eV);
  only fixed-volume steps may use a lower cutoff.
- The last step sets the ranking energy and must match BMD standards. Its
  smearing is a lab decision: MP with small SIGMA, or Gaussian SIGMA 0.05.
  (BMD relaxations currently use Gaussian SIGMA 0.2.)
- Nothing structure-dependent: `ISPIN = 1`, fixed `KPAR` (safe for few
  k-points; measured in Phase 0), `NCORE = 4`, no MAGMOM or NBANDS.
- `LWAVE = .FALSE.`, `LCHARG = .FALSE.`
- POTCARs from the shared `PBE_64` repository, same choice as the rest of
  bmd-compute, written as `Specific/POTCAR_<El>`.

Gap: the Relaxed Energy workflow has no pressure setting, so hand-off of
candidates from searches at non-zero pressure is not yet consistent.

MatterSim (later): `abinitioCode` 0 selects built-in MatterSim relaxation
(§2.8, §4.8), so a mixed ladder (MatterSim steps first, VASP after) is
possible. Out of scope until the VASP-only path works.

## 7. Sizing (illustrative)

Upper bound on VASP runs ≈ (`initialPopSize` + `populationSize` ×
(generations − 1)) × relaxation steps. Example: 20 per generation,
50 generations, 4 steps → about 1,000 structures and 4,000 VASP runs. At 4
concurrent relaxations, wall time ≈ 250 × the time of one structure's
relaxation chain, plus idle time at the end of each generation: about 5 days
at 30 min per chain, about 3 weeks at 2 h. Searches usually stop earlier via
`stopCrit`. Whether surviving structures are recalculated is **open**. Phase 0
replaces these numbers with measurements.
